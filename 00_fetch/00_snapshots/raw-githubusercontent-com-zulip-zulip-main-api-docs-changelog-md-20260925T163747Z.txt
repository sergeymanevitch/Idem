      1: # API changelog
      2: 
      3: This page documents changes to the Zulip Server API over time. See
      4: also the [Zulip release lifecycle][release-lifecycle] for background
      5: on why this API changelog is important, and the [Zulip server
      6: changelog][server-changelog].
      7: 
      8: The API feature levels system used in this changelog is designed to
      9: make it possible to write API clients, such as the Zulip mobile and
     10: terminal apps, that work with a wide range of Zulip server
     11: versions. Every change to the Zulip API is recorded briefly here and
     12: with full details in **Changes** entries in the API documentation for
     13: the modified endpoint(s).
     14: 
     15: When using an API endpoint whose behavior has changed, Zulip API
     16: clients should check the `zulip_feature_level` field, present in the
     17: [`GET /server_settings`](/api/get-server-settings) and [`POST
     18: /register`](/api/register-queue) responses, to determine the API
     19: format used by the Zulip server that they are interacting with.
     20: 
     21: ## Changes in Zulip 13.0
     22: 
     23: **Feature level 512**
     24: 
     25: * The undocumented `PATCH /users/me/subscriptions` endpoint for
     26:   updating channel subscriptions has been deprecated and
     27:   removed. It was a duplicate of the documented bulk-subscribe
     28:   ([`POST /users/me/subscriptions`](/api/subscribe)) and
     29:   bulk-unsubscribe ([`DELETE /users/me/subscriptions`](/api/unsubscribe))
     30:   endpoints, which clients should use to subscribe/unsubscribe
     31:   users from channels.
     32: 
     33: **Feature level 511**
     34: 
     35: * [`POST /messages/{message_id}/report`](/api/report-message): This endpoint
     36:   now returns an error if the message report fails to be sent to the
     37:   moderation request channel.
     38: 
     39: **Feature level 510**
     40: 
     41: * [`GET /events`](/api/get-events), [`GET /messages`](/api/get-messages),
     42:   [`GET /messages/{message_id}`](/api/get-message),
     43:   [`POST /messages/flags`](/api/update-message-flags),
     44:   [`POST /messages/flags/narrow`](/api/update-message-flags-for-narrow):
     45:   Added `hide_link_previews` as a supported [message
     46:   flag](/api/update-message-flags#available-flags) that can be
     47:   toggled by the user. When set, clients should hide auto-generated
     48:   link previews on the message for that user. Like other flags, it
     49:   appears in the message's `flags` array and in `update_message_flags`
     50:   events. The flag can be set on any message, whether or not it
     51:   currently has a link preview.
     52: 
     53: **Feature level 509**
     54: 
     55: * [`PATCH /messages/{message_id}`](/api/update-message): Fixed a bug where
     56:   passing the `stream_id` that the message is already in was processed as
     57:   a channel move.
     58: 
     59: **Feature level 508**
     60: 
     61: * [`POST /messages`](/api/send-message): Added `message_url` and
     62:   `message_link` fields to the response.
     63: 
     64: **Feature level 507**
     65: 
     66: * [`POST /users/me/subscriptions`](/api/subscribe),
     67:   [`POST /channels/create`](/api/create-channel),
     68:   [`PATCH /streams/{stream_id}`](/api/update-stream): Added
     69:   `default_push_notifications` boolean parameter that controls whether
     70:   mobile push notifications are enabled by default when a user first
     71:   subscribes to the channel, potentially overriding the user's [default
     72:   mobile notification
     73:   setting](/help/channel-notifications#configure-default-notifications-for-all-channels)
     74:   for channel messages. Only organization administrators can set or
     75:   modify this parameter.
     76: 
     77: * [`POST /register`](/api/register-queue), [`GET /events`](/api/get-events),
     78:   [`GET /streams`](/api/get-streams),
     79:   [`GET /streams/{stream_id}`](/api/get-stream-by-id): Added
     80:   `default_push_notifications` boolean field to channel objects, which
     81:   indicates whether mobile push notifications will be enabled by default
     82:   when a user first subscribes to the channel, potentially overriding the
     83:   user's [default mobile notification
     84:   setting](/help/channel-notifications#configure-default-notifications-for-all-channels)
     85:   for channel messages.
     86: 
     87: **Feature level 506**
     88: 
     89: * [`GET /export/realm`](/api/get-realm-exports),
     90:   [`GET /events`](/api/get-events): Added an `export_from_prior_server`
     91:   boolean field to the export objects returned. It is `true`
     92:   for records that were carried across a realm import; the export
     93:   happened on a previous server, so its tarball is no longer stored
     94:   on this server. This change was also backported to the Zulip 12.x
     95:   series, at feature level 499.
     96: * [`DELETE /export/realm/{export_id}`](/api/delete-realm-export): Export
     97:   records with the `export_from_prior_server` field set to `true` cannot
     98:   be deleted, as the server has no exported data to delete for them. This
     99:   change was also backported to the Zulip 12.x series, at feature level 499.
    100: 
    101: **Feature level 505**
    102: 
    103: * [`PATCH /messages/{message_id}`](/api/update-message): For requests with
    104:   `"propagate_mode": "change_all"` from users who are not administrators
    105:   or moderators, the `"code": "MOVE_MESSAGES_TIME_LIMIT_EXCEEDED"` error
    106:   response is now also returned when the target message itself is past
    107:   the time limit, as long as at least one message in the topic is within
    108:   the limit.
    109: 
    110: **Feature level 504**
    111: 
    112: * [`POST /register`](/api/register-queue), [`GET /events`](/api/get-events):
    113:   The `require_e2ee_push_notifications` realm setting, when enabled,
    114:   now completely disables legacy push notifications rather than sending
    115:   them with redacted content. This change was also backported to the Zulip
    116:   12.x series, at feature level 500.
    117: 
    118: **Feature level 503**
    119: 
    120: * [Message formatting](/api/message-formatting): The global time
    121:   syntax only recognizes ISO 8601 formatted timestamps.
    122: 
    123: **Feature level 502**
    124: 
    125: No changes; start of Zulip 13.0 development branch.
    126: 
    127: Feature level 501 reserved for future use in 12.x maintenance
    128: releases.
